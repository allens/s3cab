Architecture review — s3cab

Deepening opportunities · 2026-06-23 · ~7.8k LOC, 11 commands over a shared lib/

module seam leakage deep module

The remote engine (s3.mjs/objects.mjs/remote.mjs) and the config layer (sets.mjs/env.mjs/home.mjs) are already deep and cleanly seamed — nothing to do there. The friction is concentrated in the local snapshot pipeline: where files become a TSV snapshot file, and where that file is read back and diffed.

The walk imports the snapshot grammar and writes rows mid-walk; the command owns the pipeline glue; the format lives in a third file.

After — one deep module owns the write
interface
writeSnapshot(dir, name, {dirs, identity, files, lookup}) → path
hidden inside
header · props→TSV pipeline · #ERROR rows
#EXCLUDED rows · formatLine · zstd · temp-rename
SnapshotRow produced & consumed here
walk yields exclusion records (data) → the writer formats them. The grammar never leaves this module.
Problem

Writing a snapshot is smeared across three modules — walk.mjs imports excludedLine and writes grammar rows into a write stream threaded down through it, the command glues header + props pipeline + stringifySnapshot, and the format itself lives in a third file.

Solution

One writeSnapshot module absorbs the header, the props→TSV pipeline, error/excluded rows, and compression; walk returns exclusions as data instead of formatted lines.

  • ▸ locality: grammar stops leaking into the walk
  • ▸ SnapshotRow produced & consumed in one place
  • ▸ interface is the test surface: write path tested through one seam
  • ▸ leverage: one call writes a snapshot (now 5 lib pieces)
  • ▸ walk loses its snapshot-format dependency entirely
  • ▸ deletion test: complexity concentrates, doesn't move
Pre-1.0 (package major 0) — convention #8 sanctions bold, justified refactors. This is justified (real leaky seam + an untested write path), not speculative structure. Stays within lib/, so ADR-0023 layering is untouched.

2 · Test diff at its own interface, not through the I/O shell

Worth exploring in-process

src/lib/compare.mjs · src/lib/compare.test.mjs

Before — tests reach the deep core through I/O
22 tests in compare.test.mjs
↓ build real .tsv.zst files
compareSnapshots()
listSnapshotNames · readSnapshot · relativeToRoot · errors
diff() — 85 lines
greedy move-pairing · copy annotation

diff is exported, yet every test crosses the wider compareSnapshots seam. The deepest logic has the most expensive test access.

After — the pure core is the test surface
compareSnapshots() — thin tests
resolution + display only
— internal seam —
diff(prevMap, currMap) → classification
two Maps in, four sets out · no I/O
rotations · swaps · copies · greedy pairing
all tested in-memory, exhaustively

Category-1 dependency: pure, in-process, no adapter needed.

Problem

The deep, bug-prone core — greedy move-pairing and copy annotation — is a pure function, but every one of its tests builds real compressed snapshot files and reaches it through compareSnapshots. Edge cases are expensive to set up and bugs hide behind the I/O.

Solution

Drive diff directly with two in-memory Maps; keep a thin layer of compareSnapshots tests for resolution defaults and relative-path display only.

  • ▸ interface is the test surface
  • ▸ pairing edge cases cheap to enumerate in-memory
  • ▸ tests survive I/O and format refactors
  • ▸ no new structure — only where the tests point
Lighter than candidate 1: diff already exists at the right seam (it's exported and pure). The deepening is in the test discipline, not the code — add direct diff tests, thin out the I/O-heavy ones. Pairs with convention #12 (coverage by review).

4 · Unify the "resolved backup set" (set + applied env)

Speculative in-process

src/lib/sets.mjs · src/lib/env.mjs · src/commands/*

Before — "a resolved set" is two things, two files
flowchart TB
  CMD["any set command"] --> LS["loadSet() · env.mjs"]
  LS --> RS["resolveSet() · sets.mjs"]
  RS --> BS["returns BackupSet"]
  LS -. "side effect:
mutate process.env" .-> ENV[("process.env")]
  CMD2["resolveSet() called
directly = no env layer"] -.->|"easy mistake"| RS
  classDef leak stroke:#dc2626,stroke-width:2px,color:#dc2626;
  class LS,ENV leak
After — one call yields a fully-resolved set
resolveSet(name) → {set, env}

set membership and its env layer resolve together; no "did I call the other door?" question.

Problem

To understand a resolved set you bounce between sets.mjs (builds BackupSet) and env.mjs (loadSet wraps it, mutating process.env as a side effect). Calling resolveSet directly silently skips the env layer.

Solution

One resolution call returns the set and its resolved configuration together, instead of a value plus a global side effect.

⚠ Contradicts ADR-0022. Env is loaded at the entry point and the set layer goes through the loadSet door on purpose — the two-door split is a pinned decision. Surfaced because the friction (the resolveSet-vs-loadSet trap, env-as-side-effect) is real — but it is not recommended over the ADR without a deliberate reopening. Likely outcome: leave it, or record why in the ADR.
Top recommendation

Candidate 1 — collapse the snapshot-writing pipeline. → jump to card

It's the only candidate that fixes a genuine leaked seam — the walk importing the snapshot grammar and writing rows mid-walk — rather than just trimming surface. It concentrates the format in one place and gives the currently-untested write path a single interface to test through. Candidate 2 is a cheap, high-value follow-up that needs no structural change. Candidate 3 was investigated and dropped (the read surface is three real seams, not shallow). Candidate 4 should stay parked behind ADR-0022 unless you want to reopen it.
