1 · The loadEnv() tripwire guards a caller that doesn't exist

Heavy crosses ADR-0022

Since ADR-0055 removed the per-user env layer, loadEnv() loads nothing — its whole body is process.env.__S3CAB_ENV_LOADED = "1". What survives is a magic env var, an assert on every S3 client construction, an entry-point call, and ~30 lines of comment explaining a mechanism with nothing left to mechanise. It exists to catch “a lib consumer who skipped loadEnv” — and CLAUDE.md states there is no library surface: no main, no barrel, an entry point unsafe to import. Inside the CLI the flag is set unconditionally before any command body runs, so the assert can never fire.

Test impact (category 3)

env.test.mjs's describe("loadEnv") block asserts only that the flag is set and that a second call is inert — both delete outright, since neither asserts about behaviour. Eleven t.loadEnv() setup calls in the loadSet tests simply drop, as do the flag assignments in s3.test.mjs, s3.multipart-tuning.test.mjs and test/helpers/integration.mjs. No coverage is lost.

2 · backupLifecycle() — the caller immediately undoes what the callee did

Heavy

src/lib/aws.mjs:35 returns a BucketLifecycleConfiguration — an AWS SDK type imported for this and nothing else. Its only production consumer takes it straight back apart. Four scalars go in; four scalars come out; a whole SDK shape exists in between. Every ?. is there only because the SDK type admits undefined at each level, which the literal never does.

Today — aws.mjs:35 → :197

/** @import { BucketLifecycleConfiguration }
      from "@aws-sdk/client-s3" */

export const backupLifecycle = () => ({
  Rules: [{
    ID: "reclaim-deleted-backups",
    Status: "Enabled",
    Filter: {},
    NoncurrentVersionExpiration: { NoncurrentDays: 90 },
    AbortIncompleteMultipartUpload: { DaysAfterInitiation: 1 },
  }],
});

// …the only caller:
const [rule] = backupLifecycle().Rules ?? [];
const noncurrentDays =
  rule?.NoncurrentVersionExpiration?.NoncurrentDays;
const abortDays =
  rule?.AbortIncompleteMultipartUpload?.DaysAfterInitiation;
return `  …
          - Id: ${rule?.ID}
            Status: ${rule?.Status}
            …NoncurrentDays: ${noncurrentDays}
            …DaysAfterInitiation: ${abortDays}`;

Proposed

// Expire noncurrent versions after the DR window;
// abort stalled multiparts. Deliberately NO
// current-object expiry — never auto-delete a live
// backup (ADR-0033). Test bucket's lifecycle is the
// opposite, which is why they're never shared.
const LIFECYCLE_RULE_ID = "reclaim-deleted-backups";
const NONCURRENT_DAYS = 90;
const ABORT_DAYS = 1;

// …the caller:
return `  …
          - Id: ${LIFECYCLE_RULE_ID}
            Status: Enabled
            …NoncurrentDays: ${NONCURRENT_DAYS}
            …DaysAfterInitiation: ${ABORT_DAYS}`;

The comment — the part carrying real value — survives intact, now sitting with the constants it explains.

Test impact (category 3) — this one gains coverage

The two tests in aws.test.mjs assert on the object. They would assert on the rendered template instead: that it contains NoncurrentDays: 90 and DaysAfterInitiation: 1, and contains no Expiration: line. Strictly better — today's tests pass even if the YAML interpolation is broken, because they never look at the artifact that ships.

3 · listSnapshotNames' latest option flips the function's return type

Heavy

Small

Looked at and dismissed

Coverage is a result too — a subsystem examined and found tight is a real finding. These were read in context and judged to be earning their keep, or to be exactly the kind of seam this sweep should be suspicious of removing.

Looked like indirection, isn't

  • The registry's 18 exec adapters. Reads as 18 argument-reordering lambdas; is the parseArgs-shape → command-signature translation the registry exists to hold. Removing them pushes positionals[0] into every command body.
  • renderText's identity function. The honest degenerate case of the render layer, already settled in CLAUDE.md.
  • writeSnapshot's through seam. Two production callers with different needs.
  • uploadObjects' four-member ObjectUploader. backup uses through+transfer+result; uploadSnapshot/uploadDir use run+result. Two callers, different needs — the stated tie-break.
  • progress.mjs's due() beside update(). A measured hot-path optimisation, not a redundant member.

Duplication that shouldn't be collapsed

  • The preview-file write in delete and forget. Two callers, three lines each — under the bar. Extracting it would mint a lib seam for what is plainly each command's own I/O. The kind of extraction the sibling skill proposes and this one declines.
  • The three destructive commands' shared shape. Structurally parallel, but each gate's wording is command-specific by ADR-0030 and the policy genuinely differs (abort vs warn; typed-bucket-name vs y/N). A shared helper would parameterise five things to share three lines.
  • prompt.mjs's four readers. Distinct production callers, and a stated reason not to collapse (one readline interface for multi-line stdin).

Large, and in scale with its problem

  • The DER encoder in roles-anywhere.mjs. ~180 lines of hand-rolled ASN.1 — and the right amount: Node cannot create X.509 certificates, the alternative is a dependency, every primitive is used.
  • compare.mjs's diff. Dense, but move/rename/duplicate classification is irreducibly a three-way matching problem. Every branch reachable and pinned.
  • s3.mjs's requestErrorRelay + error table. Data-driven, one row per recognised failure. Its hasStreamBody guard has no live caller and says so — a correctness tripwire against silent object corruption is a different thing from speculative structure.
  • referenced.mjs's vocabulary module. Three production callers each, with a stated reason for living apart from its producer (keeping the AWS SDK out of three pure planners).

Method

Stage 1 ran the three queries the skill carries: code-vs-comment size, production fan-in, and exports with zero production consumers. Every hit was treated as a candidate, never a verdict. Stage 2 — the main budget — traced all 18 registered commands end to end: entry point → registry → command file → every lib module reached → the S3/filesystem boundary, asking at each hop what the layer adds, which branches that entry point can reach, whether a parameter is ever a different value, and whether the caller undoes what the callee did. Stage 3 swept the residue: the high-fan-in core (error, env, home, format, style, read-lines) and the format/protocol machinery (snapshot-file, exclude, atomic-file, env-file, the DER encoder), where uniform use hides uniform complexity. All 58 production files in src/ were read; docs/adr/ and proposals/ deliberately were not.
