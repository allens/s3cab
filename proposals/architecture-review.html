O · Two lines run on a clock, each has half of what keeps it live, and the walk's clock never ticks

A scratch harness outside the repo, importing the real progress.mjs. On a big set the walk takes minutes, and for all of it the user sees only Finding files in '~/OneDrive'… with no count and no clock. That is the freeze #277 was built to end.

Problem countedPass's doc says the walk's line cannot freeze, because the clock pulls the count. But walkDirs is synchronous all the way down, so the clock it owns never fires while the walk runs. #343 found the same starvation in the fused pass and fixed it there with a concession of its own. So the mechanism now exists in two halves: countedPass has the closing draw but never gives the loop a turn, and withProgress gives the loop a turn but has no closing draw. The rule that ties them together is one sentence in an ADR.
Solution One module in progress.mjs owns everything that makes a clock-driven line live: the timer, giving the loop its turns, and the closing draw. Its interface takes the caller's loop into account, so a caller cannot end up with a timer that never fires. The walk and the fused pass become its two adapters. How the walk gives the loop a turn is the grilling's first question, not something decided here.
Wins
  • the walk's line moves for the first time since #277
  • locality: the liveness rule lives in a module, not an ADR sentence
  • the fused pass gains its closing draw
  • withProgress's hard-coded process.stderr and copied TICK_MS go
  • the concession becomes assertable at one interface
  • countedPass's doc becomes true
Why it hid: the test yields the loop that the walk never yields. progress.test.mjs's "redraws on its own clock while the caller does nothing at all" waits with await setTimeout (:198, :203), and that wait gives the loop a turn. Pass 11 verified #277 the same way: "a pass whose caller only sleeps advanced 0 in 1 sec". The 402,000-file pty run that "showed the count jump straight from the bare label to 2,000" was a starved timer, not the excluded descent yielding nothing. A test of a clock-driven line needs a caller that does not yield. Otherwise it tests the clock and not the line.
Amends ADR-0076, does not contradict it. ADR-0076's decision, a line driven by a clock, stands. This moves its own consequence ("any future pass … inherits the same obligation") out of prose and into the module. #343's limit stays as written: a turn between rows cannot preempt one long synchronous row, and the chunked-read fix was declined. Questions for the grilling: should the walk go async, or should the line offer a per-item check gated on due()? The excluded-subtree descents, which yield no file at all, have to reach it too. And does the concession also keep the park handlers responsive (snapshot-file.mjs:184, :217)? That would be a second job nobody has written down. It is unverified.

A 280,232-file run died three hours in. The work file decompressed cleanly: whole rows, one torn final line, no #END.

After — completeness is a return value; recovery rides the acquire

None of ADR-0048's rejected heuristics: no .lock, no PID liveness, no age-based auto-break.

Problem Completeness is asserted rather than returned, so a hard-killed run's rows are unreachable through the interface even though the parked-lookup reader and the no-trust-boundary default are already in place to consume them.
Solution Make completeness a returned fact, and do the recovery as a rename at the moment withSnapshotFile wins the wx acquire — not at read time.
Wins
  • truncation becomes a string, not a kill
  • recovery needs no liveness heuristic
  • three hours of hashing stops being free to lose
Where it is done matters more than the parser change. readBaseline runs before generateSnapshot enters withSnapshotFile, so reading the stale work file at baseline time reads a file another live run may own — the lock has not been taken yet. That half needs design; the parser half is small and safe.

Examined and found deep — skip future runs

Pass 14: every other line on a clock or a push was checked, and they tick. The store LIST's counted pass and both of find's are fed by real async I/O (a network page, a zstd/readline stream), so their timers get turns. restore pushes on due() over real async writes and owns no timer. The per-file upload bar in s3.mjs is driven by the SDK's progress events. network-status.mjs has no timer at all. O is the walk and the fused pass only, which are the two places where synchronous work runs in front of a timer.

Pass 12's own landings all hold up. bucket-scan.mjs — the ordering invariant is the body, not a comment at two call sites, and its test pins it at the s3.mjs seam including the half a call-order assertion cannot see (a held snapshot GET proving the objects LIST has not begun). test/helpers/s3-seam.mjs — the asymmetric defaults (reads: coherent empty store; writes: throw) are a real argument, and test/s3-seam.test.mjs keeps the surface honest in both directions and guards its own blind spot. test/helpers/enumeration.mjs — fixtures go through the production fold, so a test cannot hold a shape a real read would not produce. format.mjs's localMoment/completionInstant/readClock — one clock read behind both doors, round-up rule argued and pinned (pass 13's A, about the two callers that bypassed it, landed in #348). safeSize/sizeDisagreements and referenced.mjs's unreadableMessage — two real adapters each. auth.mjs + roles-anywhere.mjs after the RolesAnywhereSessionError landing — the identity/session split is decided by error type at the throw site and caught by type, never by message, and transport errors are deliberately let through raw so the relay retries them.

Re-confirmed from earlier passes. progress.mjs's core mechanic; objects.mjs and atomic-file.mjs; uploadObjects/planUpload/storedHashes; withSnapshotFile's three release paths (candidate H adds to its acquire, it does not restructure it); planRestore taking exists as a parameter; network-status.mjs's refcount proxy, whose mis-announcement under a one-in-flight pass is recorded deliberately in ADR-0091 and pinned as intended; s3cab.mjs, commands.mjs, help.mjs; walk.mjs's walkDirs/assertWalkableDirs/resolveWalkRoot; sets.mjs's validateBucketName, which is a clean parameterized seam rather than the split rule it resembles.

Checked and discarded as findings. render.mjs's remaining hand-built blocks — sentence headings and column alignment, a different shape from section()'s label+list, so folding them in would widen the interface more than it saves. snapshot.mjs's bytesTotal pre-pass — not a hot-path cost: walkDirs already materializes files, so it is O(n) Map lookups with no extra syscall. Top recommendation

Take this one first

O — one clock-driven line that keeps its own loop turning

It is the only candidate with a fault a user meets on every big run: the walk's line sits on its bare label for the whole walk, which is minutes on the sets this tool is for. And the fault was shown by running the real module, not inferred from reading it. The fix the walk was promised in #277 never took effect, and #343 has just rediscovered the same cause from the other side. So the knowledge is fresh, the two halves of the mechanism are both in view, and there are already two adapters with genuinely different loops. That makes it a real seam, not a hypothetical one. It should go first among the snapshot.mjs track, ahead of F, I and P, which all edit the same function.

Runners-up, unchanged from pass 13: B (the classifier that does not classify) and C (a wrong number on the strongest confirmation prompt the tool has). Both are independent of O and of each other.
