A · One PUT loop — uploadDir is the third source that never joined it

Strong carries a live correctness gap

Files

src/lib/upload.mjs — the module header (l.12–27), uploadObjects (l.192), fileChange (l.270), uploadDir (l.387)

src/commands/upload.mjs — --dir dispatch (l.138–160), --file dispatch (l.125–135)

Problem

upload.mjs's own header states the design: "One PUT loop, one drift guard, two sources." That sentence arrived with ADR-0069 (#245) and is not true of the module it heads. There are two PUT loops and three sources. uploadDir — added earlier, in #227 — hand-rolls its own seen-dedup + putObject loop, and #245 built the shared transform beside it without folding it in.

The consequence is not stylistic. uploadObjects re-checks size+mtime between hashing a file and PUTting its bytes, and its own doc explains exactly why: "the store trusts the hash on write, so PUTting its current bytes would file them under the recorded content's hash — corrupting that object for every snapshot and path that dedups to it, surfacing only at restore." uploadDir has the identical hash-then-PUT window and no guard at all: fileProps(path) reads and hashes the whole file, then putObject streams it again from disk.

And the window is widest for exactly the files upload --dir exists to serve. It is the "seed my priority folders before the initial backup" primitive (docs/design/backup.md), and those folders are the multi-GB video population, where hashing one file takes minutes before the PUT re-reads it. upload --file shares the shape (prop() then putObject) at one-file stakes.

All three paths become row sources for one transform. The guard cannot be missing from a path, because there is only one path.

Solution (sketch — for grilling, not settled)

uploadDir becomes a row source rather than a second engine: walk → hash → yield [path, Props], and run those rows through uploadObjects with an empty stored set (its current design point: the conditional PUT is the already-stored check, so no LIST and no baseline). Its seen/uploaded counters and the { candidates, uploaded } return are already exactly what uploadObjects.result() reports.

Open questions worth grilling: the seed writes no snapshot, so what should a drifted file do — record a FileChangedError naming a re-run (the transform's contract) or skip and count it? And the drift error names s3cab backup <set>, honest advice for a seed too, but worded as though a snapshot was written.

Benefits

  • Leverage: the guard, the dedup, the counting and the stop-on-first-transport-failure policy arrive with the transform. Every future object source inherits them instead of re-deriving them.
  • Locality: "how does s3cab put an object into the store, safely" becomes one function to read. Today the answer depends on which of two loops the caller reached.
  • Tests: the drift cases are already covered against uploadObjects' interface (mock-free, over in-memory rows). Routing uploadDir through it puts the seed path under that existing suite rather than needing a parallel one.
  • The header stops lying — "one PUT loop, three sources" becomes a checkable statement (doc-discipline rule 1).
Also a bug, independently of the refactor. The missing drift guard on upload --dir belongs in proposals/bugs.md whether or not this candidate is taken — a two-line fileChange call would close it. The architecture argument is about why it was missing in the first place.

D · The bucket's unreadable snapshots have no name

Strong missing seam · earns a CONTEXT.md term

Files

src/lib/cleanup.mjs — typedef l.44, flatMap l.74–76

src/lib/unrestorable.mjs — typedef l.56, flatMap l.94–100, display l.294

src/lib/delete.mjs — typedef l.79, flatMap l.105–107, display l.389

src/commands/cleanup.mjs l.107–116 · src/commands/delete.mjs l.154–163 — the two aborts

src/lib/verify.mjs l.43 · src/lib/remote.mjs l.234–262 — where it originates

Problem

referencedObjects yields per-set results carrying unreadable: { snapshot, reason }[]. Every consumer wants the same derived thing — the whole bucket's unreadable snapshots, qualified by which set they belong to — and every consumer builds it itself: 

// cleanup.mjs:74, unrestorable.mjs:94, delete.mjs:105 — three times, identical
const unreadable = [...referencedBySet].flatMap(([set, r]) =>
  r.unreadable.map((u) => ({ set, snapshot: u.snapshot, reason: u.reason })),
);

// …then declared as an inline structural type, three times
@property {{ set: string, snapshot: string, reason: string }[]} unreadable

// …then rendered, four times
const where = plan.unreadable.map((u) => `${u.set}/${u.snapshot}`);

Ten copies of one concept across five files, and it has no name — not a typedef, not a CONTEXT.md term. The tell is the last line: set/snapshot is a user-facing identifier for a snapshot inside a bucket, invented independently in four places. And two of the sites build the same abort from the same skeleton ("Can't … safely: N snapshot(s) won't read … Unreadable: … Triage first: s3cab verify <bucket>"), differing only in one middle clause — which is precisely the "heavy, actionable, reused → a named factory" row of error.mjs's own taxonomy.

Benefits

  • Locality: the three plan modules stop carrying an identical six-line preamble that has nothing to do with their actual question (orphans / unrestorable files / deletable objects).
  • Leverage: the widened type stops being three structural literals that can silently drift apart — the type checker starts holding one contract instead of three coincidences.
  • Vocabulary: a CONTEXT.md term for the qualified set/snapshot name, which currently exists only as a template literal repeated four times.
  • Tests: the abort's wording is asserted per command today; a factory makes the shared skeleton assertable once and leaves each command's own clause as the thing worth testing there.
Placement is the grilling question, not the existence. remote.mjs produces the per-set results; verify.mjs owns the ReferencedResult typedef the three modules @import; error.mjs hosts the taxonomy the abort factory belongs to. Splitting the derivation and the message across two homes may well be right — that is the conversation, and it decides whether this lands as one small module or as two additions to existing ones.

B · The consequence-summary table, built twice; count/plural, built four times

Worth exploring

Files

src/lib/unrestorable.mjs — formatUnrestorableSummary l.242–277, files l.379, objects l.382

src/lib/delete.mjs — formatDeleteSummary l.306–341, files l.434

src/lib/deletion-record.mjs — files l.179, inline "stored object(s)" l.166

src/render.mjs — count l.825, plural l.830 — private, ~20 call sites

Problem

delete.mjs's doc says it outright: the per-path table "follows the unrestorable summary's shape exactly". It does — by copy. Both compute three column widths, close over the same row() renderer, pop the total, draw the same ─ rule at fileCol + byteCol + 2, and both append a shared across N … line under the same sole-vs-shared rule. Roughly 30 lines, near-verbatim, in two files.

Underneath it, the smaller duplication: render.mjs already has count and plural — but private, so the three lib modules that need them each hand-rolled files(n), and two hand-rolled objects(n) as well. The ninth pass logged this as "pluralization hand-rolls outside render.mjs's plural (marginal)"; the deletion rework has since tripled it.

Before

unrestorable.mjs

width calc · row() · rule · total · files() · objects()

delete.mjs

width calc · row() · rule · total · files() · inline objects

deletion-record.mjs

files() · inline objects

render.mjs

count() · plural() — private, unreachable

After

the counting primitives

count() · plural() — one home, render.mjs included

one aligned-total table

rows + total → padded lines + rule

unrestorable.mjs / delete.mjs

choose the rows and the labels — the part that actually differs

Each summary keeps its own prose, headline and warnings; only the alignment mechanic moves.

Benefits

  • Locality: "why do the numbers line up like that" becomes one function with one doc comment. Today the reasoning ("right-align the numbers so the magnitudes line up") is written out in one file and silently copied into the other.
  • Tests: alignment is fiddly and currently asserted only through two whole rendered summaries. A table primitive is testable directly — including the case that would break both copies (a byte figure wider than its header).
  • The next destructive command's preview gets the house table for free, rather than a third copy.
Why only "worth exploring". Two arguments cut against it, and both are real. (1) These are two different commands' user-facing output, and deliberately-similar-today is not must-stay-identical — a shared renderer couples them, and ADR-0006/#5 has form against exactly this kind of presentational machinery. (2) render.mjs is the render layer (ADR-0043), yet these summaries deliberately bypass it because they are pre-decision output printed before the command returns — so "put the table in render.mjs" may be the wrong home even though that is where its siblings live. Grilling should probably split the candidate: the count/plural half is cheap and clearly right; the table half is a judgement call.

C · putText re-spells putObjectParams, and PreconditionFailed has no isObjectNotFound twin

Worth exploring small · inside one module

Files

src/lib/s3.mjs — awsOnlyPutParams l.593, putObjectParams l.619, putFile's catch l.677–688, isObjectNotFound l.708, putText l.752–775

Problem

awsOnlyPutParams' doc claims the gating rule "lives in one place", shared by "putFile (via putObjectParams) and putText". Half true. The AWS-only gating is shared; the rest of putObjectParams' body is re-typed inside putText — its own parseS3Uri, its own awsOnlyPutParams() spread, its own IfNoneMatch: "*" conditional. So the conditional-PUT spelling exists twice in the module whose entire job is to be the one SDK boundary.

Then the mirror image: both uploaders map PreconditionFailed → false with the same four-line Error.isError(error) && error.name === … guard. The module already has the pattern for this — isObjectNotFound, whose doc gives the reason: "the single spelling of 'missing object' for this SDK boundary, so callers don't each repeat the SDK's names." "Already there" is the same kind of fact, and it is spelled twice.

Benefits

  • Locality: a future change to how s3cab writes objects (a new AWS-only param, a different no-clobber mechanism) is one edit, not two — and the second is easy to miss, because putText's copy doesn't look like a copy.
  • Tests: putObjectParams is already exported and asserted directly (pure, no upload). Routing putText through it puts the marker/config write path under that existing coverage.
  • The predicate names the concept the way the module names its sibling — consistency of interface, which #5 explicitly counts as "simpler".
Check before touching: the standing rejection on parameterizing putFile's no-clobber mechanism is adjacent but different — that one was about making the HEAD-preflight vs conditional-PUT division of labour configurable, and stays rejected. This changes no mechanism and no round trip; it only stops the same mechanism being written twice. Worth re-reading that entry during grilling so the two don't get conflated.

Examined & left alone

Read this pass and deliberately not candidates — recorded so future runs skip them.

  • The destructive-command pattern across delete / forget / cleanup (ADR-0064). The non-interactive gate is structurally identical three times — but it is three lines, and the substance is the bespoke ADR-0030 message each one needs (naming its own --dry-run/--force invocation). A helper taking the whole message is shallow: deleting it would move complexity, not concentrate it. Drift risk is already covered — each command has its own "refuses a non-interactive run without --force" test.
  • The three shapes of the deletion-record lookup — verifySet takes Map<hash, {deletedOn}>, planCleanup takes Set | Map<hash, unknown>, baselineHashes takes Iterable<hash>. Looks like a scatter; isn't. Each asks a genuinely different question (when was it deleted / is it a member / subtract these), and one unified value would serve none well. Same reasoning that declined the credentialMode classifier.
  • The network-resilience trio — s3.mjs's requestErrorRelay, network-status.mjs, the requestErrorTable. Deep: the relay is exported and pure of a live client, the error table is data not branching, and network-status.mjs justifies its module-level state explicitly (the terminal is one shared resource; the outage is one fact about the run). The curried-window signature even carries the bug it prevents in its own doc. Exemplar alongside the SigV4-X509 signer.
  • lib/snapshot.mjs and the fused pipeline (ADR-0069). The through seam is the cleanest kind: one optional transform parameter is the entire difference between snapshot and backup, and backup.mjs is thin porcelain over it. The never-throw-mid-stream contract is stated where a future editor will read it.
  • command-details.mjs (#222) — a clean prose extraction with a stated invariant ("every command details string lives here"), no imports, and the "short one-liners stay inline" boundary written down. Nothing to deepen.
  • The plan/execute discipline, again clean — planDelete, planUnrestorable, planRestore, planCleanup, verifySet and planUpload are all pure and all say so. The deletion rework followed the house pattern rather than inventing one; candidates B and D are duplications between these modules, not failures of the split itself.

Top recommendation — A

Fold uploadDir into the one PUT loop. It is the only candidate that closes a correctness gap rather than a tidiness one: upload --dir can today store the wrong bytes under a hash and corrupt that object for every path that dedups to it, surfacing only at restore — the exact failure ADR-0069 wrote the drift guard to prevent, on the path built for the multi-GB files where the window is minutes wide. The refactor and the fix are the same change, the blast radius is one module plus its existing test suite, and it makes the module header's own claim true.

Then D — the largest genuine duplication found (ten copies of one unnamed concept across five files), and the one that earns a CONTEXT.md term. It has an open placement question worth grilling before any code moves. C is a cheap ride-along the next time s3.mjs is open. B should be split in grilling: take the count/plural half, decide the table half on its merits.
