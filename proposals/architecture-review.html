5 · Thread the previous snapshot through snapshot → compare

Worth exploring hot path

src/commands/snapshot.mjs:43–47, 81–85 · src/lib/compare.mjs:113

sequenceDiagram
  participant S as snapshot
  participant D as disk (.tsv.zst)
  participant C as compareSnapshots
  Note over S,C: Now — previous snapshot decompressed + parsed TWICE
  S->>D: readSnapshot(previous) — hash-reuse lookup

Problem. The previous snapshot is fully zstd-decompressed and per-entry parsed twice per run — once for snapshot's hash lookup, again as compareSnapshots' baseline. Exactly the per-file-overhead the hot-path convention warns about, at whole-snapshot scale.
Solution. Thread the already-parsed since entries through the compare seam, or have snapshot compose the pure diff directly with what it already holds. (The new-side re-read is cheap to keep — it doubles as round-trip verification.)
  • one decode per run, not two
  • data threaded through interface
  • no module-level cache
  • pairs with candidate 6

Top recommendation

Candidate 1 — extract a pure cleanupPlan

It's the freshest and highest-leverage. The design doc asserts cleanup is verify's twin, but only verify realized that in code (the pure verifySet); cleanup's orphan + grace-window + missing/damaged arithmetic is trapped inline in the async command, testable only by mocking S3.
