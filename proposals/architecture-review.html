Verdict

Most of the stretch is the fifteenth pass's own landings (#366–#380). They hold up: each new seam is used through its interface and tested there. Five things are new: gzip in place of zstd (ADR-0097), exclude lines offered for files that failed last time (#385), names with line breaks (#388), an empty exclude.txt (#374), and the progress wording (#382). That new behaviour is where the friction is.

This pass's main shape: a module writes a path into a grammar it doesn't own. Backup builds an exclude line without the rules that read it back. tree writes a tab-separated row without the rule that guards the snapshot's rows. The codec check is split, so the damage classifier has to know zlib's error codes. A second shape: a helper split out for exactly one second caller makes the safety step an optional argument, and that caller leaves it off.

The case it gets wrong

  1. The latest backup holds h1. The file is still on disk.
  2. s3cab delete h1 removes the object and records it.
  3. backup subtracts the record, so it uploads h1 again.
  4. status doesn't read the record, so it says h1 is backed up and reports 0 to upload.

That breaks "so status and backup never disagree" (status.mjs:13) in the direction its own doc rules out: status may report more than backup sends, never less. Every other reader of a remote snapshot reads the record.

Problem
baselineHashes was split out "because status wants exactly this", and status is the caller that leaves its deleted argument off.
Solution
Move the deletion-record read inside, so storedHashes' trusted branch and status both get it. baselineHashes then becomes private, or its deleted argument becomes required.
Wins
  • Locality: the record is subtracted in one module
  • Leverage: two callers, neither can skip it
  • The interface loses its optional safety argument
  • status gets its first test through the seam
Tests
The header of status.test.mjs says the remote diff "is exercised end-to-end by the e2e suite". It isn't: no file under test/ calls status. The control grep for backup and restore finds six. Since the twelfth pass, the s3Seam stencil can fake this without a bucket.

Problem
#388 taught the snapshot writer to spell out an excluded name that has a line break. The other tab-separated output, renderTree's, writes `${path}\t${pattern}` as it comes, although its doc chose a tab "for the same reason snapshots use one: no quoting, no escaping". Solution

  • A renderTree test pins one record per line

Problem
A gzip failure only counts as damage because two modules happen to agree on zlib's error codes. No test feeds non-gzip bytes through the real reader into the classifier. The scan test throws a hand-built Z_DATA_ERROR from getStream, which is where real S3 errors come from, before anything is decompressed.
Solution
The reader turns every codec failure into its own damage error and leaves the source's own errors raw. That keeps integration remote.test.mjs's "a dropped connection is not damage" true.
Wins

  • One table test: bad bytes in, finding out

Top recommendation

Status forgets the deletion record

It breaks a promise the module states about itself, and it fails right after a delete, when a user most needs to hear that the next backup will upload that content again. The fix makes a module deeper: one function owns what the cloud vouches for, and the optional safety argument goes. It also gives a command with no real test its first one, through a seam that already exists.
