Headline: the new subsystem is mostly deep

roles-anywhere.mjs is a genuinely deep module — ~700 lines of DER / X.509 / SigV4-X509 machinery behind ~11 small exports, with the ~180-line DER encoder fully private. The signer path is the in-repo exemplar of the pattern this project keeps missing: a thin I/O core (createSession) flanked by two extracted, unit-tested pure functions (buildSignedRequest, parseSessionResponse). onboarding.mjs is likewise pure text-generation, asserted directly with zero mocking. The friction is concentrated in one adjacent function, one implicit cross-module contract, and the scatter of "which credential mode is this set in?" — not in the core design.

A · Extract a pure arnsFromOutputs

The stack-output → env-record mapping is trapped behind the CloudFormation SDK call.

Strong · top pick

Files

  • src/lib/roles-anywhere.mjs:465–505 (saveArnsFromStack)
  •   pure part: 482–501
  • src/lib/roles-anywhere.test.mjs:211–285 (mock.module)

Problem

saveArnsFromStack fuses three concerns: an identity-exists precondition (I/O), a lazy SDK import + DescribeStacks (I/O), and a pure step — iterate Outputs, map OutputKey → the three S3CAB_RA_* env keys, compute the missing list. That pure "given outputs, produce the env record or the missing-key list" logic — the part a reviewer actually cares about — is reachable only by mocking the whole @aws-sdk/client-cloudformation module. This is the project's named recurring weakness verbatim: plan/execute interleaving pushing pure decision logic behind I/O-only test access.

Solution

Extract arnsFromOutputs(outputs) → { arns, missing } as a pure exported function. saveArnsFromStack shrinks to fetch-and-delegate: precondition → DescribeStacks → arnsFromOutputs → throw-or-write.

Benefits

Locality: the output-shape knowledge (which is a contract with the template) sits in one named unit. Leverage: the missing-outputs branch — today only hit through a mocked SDK — becomes a plain array-in, object-out unit test. It follows the exact split the signer already models (parseSessionResponse beside createSession). Convergent: two independent explorers surfaced this as their #1/#2.

✓ Deletion test: passes — concentrates the mapping+validation into a directly testable unit; no complexity moves. Zero ADR tension (implements the ADR-0056 --save --from-stack step; a helper doesn't touch the decision).

D · Teach authNotice the Roles Anywhere mode

A user-visible promise silently degrades for exactly the new mode.

Strong

Files

  • src/lib/s3.mjs:70–82 (authNotice)
  • src/lib/s3.mjs:155–161 (its caller client())
  • src/lib/s3.test.mjs:277–327 (no RA case)

Problem

authNotice knows three shapes — profile, endpoint, generic fallback. client() feeds it {profile, profileSource, endpoint}. But an RA-mode set carries no profile and (RA is AWS-only, mutually exclusive with a custom endpoint) no endpoint — so every Roles Anywhere command prints the anonymous "Contacting the cloud…". The docstring's promise — "'which account am I about to touch?' never needs guessing" — degrades for the one mode where the identity is known (isRolesAnywhereMode()). The fourth mode was added to the resolver without widening its paired notice (or its tests).

Solution

Pass an RA signal into authNotice (or, once candidate C lands, the resolved mode) so it can print e.g. "Using Roles Anywhere (keyless)". Add the missing s3.test.mjs case.

Benefits

Closes a defect-shaped gap in the SDK boundary's one job. Standalone-cheap today; even cheaper as the first beneficiary of a credentialMode() concept (C) — which is why this is the concrete symptom that motivates C.

Before
$ s3cab backup work
Contacting the cloud…          ◀─ anonymous
… (RA-mode set: no profile, no endpoint)
After
$ s3cab backup work
Using Roles Anywhere (keyless)  ◀─ traceable

✓ Deletion test: n/a (widening, not a boundary). ✓ ADR: consistent with ADR-0057 — the notice simply wasn't widened alongside resolveCredentials.

B · One RA stack-output ↔ identity-env contract

Three ARN key names, spelled by hand in three files — an implicit contract held together by matching string literals.

Worth exploring

Files

  • onboarding.mjs:299–305 — template Outputs (producer)
  • roles-anywhere.mjs:445–449 — ARN_ENV (map)
  • roles-anywhere.mjs:559–566 — readSigningIdentity (read)

Problem

The names TrustAnchorArn / ProfileArn / RoleArn and their env twins S3CAB_RA_* exist only as matching literals in three spots. onboarding.mjs doesn't import from roles-anywhere.mjs, so nothing binds them. Rename an Output and --save silently fails with "missing the Roles Anywhere outputs" — an error that even blames the user's stack. Within roles-anywhere.mjs the env keys are then spelled twice more: ARN_ENV values (write) vs literal property reads in readSigningIdentity (read).

Solution

Promote the three (output-name → env-key) pairs to one shared constant, consumed by the template generator, arnsFromOutputs (candidate A), and readSigningIdentity. The template's Outputs: block and the reader then can't drift.

Benefits

Locality: the round-trip contract becomes one symbol instead of a tacit convention. Pairs naturally with A (both touch the same seam) — A makes the mapping testable, B makes the vocabulary single-sourced.

C · A pure credentialMode() classifier

"Which of the four modes is this set in?" is re-derived from raw env keys at five-plus sites, with three internal spellings of the concept.

Worth exploring
⚠ Sits on the ADR-0055 line. ADR-0055 keeps auth as "a bag of AWS_* variables handed to the chain," and a prior review parked restructuring the config layer. A read-only classifier is arguably new surface (an adapter over the bag), not a restructure — but this is a decision, not an obvious win. Do not fold the write-side mode-clearing into it (that would drag the file-write across the seam and fail the deletion test — one explorer verified this).

The scatter

  • auth.mjs:435 — isRolesAnywhereMode() route
  • auth.mjs:69–126 — credentialCase (5th case)
  • commands/provider.mjs:296–322 — newMode ("ra")
  • commands/provider.mjs:88–129 — describeScope
  • commands/provider.mjs:164–181 — shellNote
  • s3.mjs:70–82 — authNotice (RA-blind, cand. D)

Problem

No function answers "which mode does this set declare?" Each site re-derives it from raw env keys, so adding RA meant adding a fourth arm to every one. The concept is stringly-typed and inconsistent: the flag/key is "roles-anywhere"/RA_MARKER, the internal literal is "ra", callers elsewhere use a rolesAnywhere boolean. And the marker read drifts: === "1" in two places but a loose truthy at provider.mjs:319 — so S3CAB_RA=0 reads as not-RA everywhere except the clear-on-replace path (latent bug).

Before — every reader re-derives

         AWS_ACCESS_KEY_ID, S3CAB_RA}
   │  │  │  │  │
   ▼  ▼  ▼  ▼  ▼   (5+ ad-hoc derivations)
authNotice  credentialCase  newMode
describeScope  shellNote  isRolesAnywhereMode
   "ra" / "roles-anywhere" / rolesAnywhere
   === "1"  vs  truthy   ◀─ drift
After — one classifier

  → "profile" | "keys" | "ra" | "ambient"
       │
       ▼  (one pure, unit-tested source)

shellNote · resolveCredentials
   one spelling · one marker rule

✓ Deletion test: a read-only classifier concentrates five derivations into one pure function and kills the naming/truthiness drift — provided the execute-side clearing stays put. Biggest leverage here, but the most contentious; grill the ADR-0055 boundary first.

E · Consolidate the RA onboarding recipe prose

The porcelain hand-writes recipe text that its own header says lives (pure, unit-tested) in onboarding.mjs.

Worth exploring

Files

  • commands/aws.mjs:126–138 (saveRolesAnywhere confirmation)
  • onboarding.mjs:410–416 (near-verbatim closing)
  • setup.mjs:115–123 (rolesAnywhereNotReadyError)
  • roles-anywhere.mjs:467–471 (precondition error)

Problem

saveRolesAnywhere inlines ~7 lines of "point a backup set at it" wiring prose near-verbatim to the close of awsRolesAnywherePlan — while aws.mjs's own header comment claims "the recipe text lives in onboarding.mjs (pure, unit-testable)." The command string s3cab aws --roles-anywhere --save --from-stack … recurs in four files. Understanding "how a bucket gets onboarded via RA" means bouncing aws → roles-anywhere → onboarding → setup.

Solution

Move the save-confirmation into an awsSaveConfirmation({dir}) generator in onboarding.mjs; have the duplicated command strings reference shared name-builders (stackName et al. already exist there).

Benefits

Locality: all recipe prose back in its one pure, unit-tested home, restoring the invariant the header already asserts. The confirmation string — today reachable only through the async I/O path — becomes directly testable.

✓ Deletion test: partial — the human-in-the-loop workflow is inherently multi-command, so it doesn't fully collapse, but the duplicated strings concentrate. ✓ ADR-0056/0034 (thin porcelain, "the plan is the result").

Examined & left alone

Verified against source and judged not deepening candidates — recorded so the next run skips them.

  • The SigV4-X509 signer — cite as the exemplar. createSession is a thin I/O core flanked by pure, independently-tested buildSignedRequest + parseSessionResponse; the socket-timeout concern is isolated in its own node:https-mocking test file. This is the pattern candidate A is missing.
  • RA credential arm untested at unit level (auth.mjs:409–422, 434–437). The one bespoke credential arm s3cab owns is exercised only by the gated integration suite; the new Date(expiration) shaping could be cheaply unit-covered. A coverage observation (ADR-0020: judged by review), not a module boundary — worth a test, not a refactor.
  • The buildSignedRequest RSA branch (roles-anywhere.mjs:674–683) is dead relative to the codebase (buildIdentity only emits P-256) — but ADR-0058 discusses key type and reference-helper parity is cheap. Characterize, don't act.
  • readSigningIdentity's catch-all (575–580) conflates "not usable" with "crashed" — a genuine bug in the read path is reframed as setup advice. Defensible & documented; narrowing it moves nothing. Marginal.
  • saveArnsFromStack's CloudFormation dependency gives the crypto/storage module control-plane knowledge — but it writes the identity's private env, which only this module owns. Moving it out would leak the file layout. Keep.
  • set-marker.mjs pure parsing behind S3 I/O (listRemoteSets / readRemoteInfo) — same shape as A but tangential to onboarding; mild, and it's setup's remote marker, not a credential seam.
  • aws-profiles.mjs shallow wrapper — interface ≈ body, but inlining moves the try/catch + undefined-sentinel into its one caller. A legitimate thin adapter over the SDK parser. Not a deletion candidate.
  • Region-default chain (aws.mjs:73–77) duplicates scripts/setup-test-bucket.mjs. Minor policy dup.

⭐ Top recommendation

Tackle A (extract arnsFromOutputs) first. It is the one finding two independent explorers converged on, it is the textbook instance of this project's named recurring weakness (pure logic reachable only through mocked I/O), it has the smallest blast radius, zero ADR tension, and an immediate test win — and it follows the split the signer in the same module already models. B rides along naturally (same seam: A makes the mapping testable, B single-sources the ARN vocabulary). D (RA-blind authNotice) is a cheap, user-visible defect fix and the concrete symptom that motivates the deeper, more contentious C (a pure credentialMode() classifier) — grill C's ADR-0055 boundary before committing to it. E is a tidy locality win whenever the recipe prose is next touched.
