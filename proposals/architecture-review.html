Solution The module owns its temp from creation to rename, so any failure it can name removes the temp before the error leaves. A torn stream stays the documented exception. The two restore docs that describe refusal at creation get rewritten to the new fact.
Wins

  • the module's stated rule becomes true
  • locality: the cleanup stays in one module
  • first test that asserts no temp remains
  • two stale "measured" docs get corrected

No test anywhere asserts that no s3cab-tmp file is left. And both restore docs say the codes were "measured": they were, at temp creation, before #365 moved the failure.
A trade-off to record, not hide. Removing the temp fixes the litter, not the wasted download. Refusing before the download would mean probing the final name first. That is a design question for the grilling, not part of this card. Separately: this is a live defect, and proposals/bugs.md is the defect tracker, which #365 had just emptied. R — the temp belongs to writeFileAtomic until the rename succeeds

It is the only candidate a user meets as damage: a restore that finishes green leaves full-size hidden files in the tree they asked for, one per refused name, and downloads each one first. It shipped today in #365, the HEAD this pass read, so the change that caused it is fresh. It was shown by running the real module on both filesystems, not inferred. The fix is inside one module that already removes its temp on the other failure, and the test needs no S3 and no mock: a stream, a temp directory and a name the filesystem refuses. It also unblocks T, which rewrites the restore loop R's fallback sits in.

Runners-up: S (the cheapest card here, and a rule the codebase already states correctly one file over) and C (a wrong number on the strongest confirmation prompt the tool has, now also on stdout). All three are independent of each other.
