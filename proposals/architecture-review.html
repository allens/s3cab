A · find cannot see a UNC path

Strong live fault
src/lib/path-match.mjs:9-28 — isWindowsPath
src/lib/find.mjs:181-191 — prepare
src/lib/find.mjs:133 — compileFindPattern

Before — one predicate, two questions

After — ask the question you mean

toPosixPath(path) → { path, base, foldCase }

drive-letter roots
UNC roots
posix roots
basename cut
separator fold

One module answers “how is this path spelled?”, and its answer is a record, not a boolean two callers read differently.

Problem

isWindowsPath is documented as a case predicate, and its UNC exclusion is deliberate and correct for that question — a remote filesystem sets its own case rules. find.mjs's prepare then borrows it to decide a different question: whether to treat \ as a separator. For \\nas\photos the two answers diverge, and every consequence is silently wrong at once — the basename cut, the separator normalisation, and the case fold.

Solution

Deepen path-match.mjs from two loose predicates into the module that owns path spelling: one entry point that returns the normalised path, its basename and whether comparison folds case, with the three root shapes handled inside. Callers stop deriving one property from another's answer.

The live consequence

A member directory on a NAS share is backed up fine — nothing in setup or the walk refuses a UNC root — and then cannot be found. Under ADR-0089 find is the only documented route to the content hash that delete takes as its operand, so a whole class of backed-up file cannot be removed by the workflow the guide describes. There is no src/lib/path-match.test.mjs at all, so nothing was ever going to catch it.

Wins

  • the fault disappears rather than being patched
  • locality: three root shapes, decided once
  • a seam that has never had a test, gets one
  • find/delete work on NAS content
  • leverage: restore --output asks the same module
  • the doc comment stops being load-bearing for a second reader
Consistent with ADR-0088 — the ADR put the shared glob grammar in path-match.mjs on purpose. This finishes that move: the module currently exports the grammar and half of the spelling question.

The RA branch returns at :681, outside the try — so a runtime RA failure never picks up the set / profile / endpoint context, and lands in requestErrorTable as a plain Error that matches no row.

Problem

“s3cab could not get credentials” is one user-facing concern with two independent implementations: the noCredentialsError / requestErrorTable family, matched by name and errno, and RA's four hand-written plain Errors. The messages are individually decent — but nothing composes them, nothing adds set context to the RA ones, and a fifth failure mode added to either family will not appear in the other. Meanwhile setup --roles-anywhere refuses without an identity (setup.mjs:271) and provider --roles-anywhere does not, because the shared knob-gatherer in lib/provider.mjs — the one module both commands go through — doesn't know the rule.

Solution

Make “resolve credentials for this set” a single deep module: RA inside the same try, its failures shaped by the same factories, and the readiness rule owned by the shared mode-gatherer so both commands inherit it rather than one remembering it. The seam is already named — resolveCredentials is the interface the SDK holds.

The test surface

resolveCredentials is imported by exactly one file in the repo — src/lib/s3.mjs:29, production. No test imports it. parseSessionResponse is pure and well tested, which is precisely the skill's warning: the pure function was extracted for testability, and the defects live in how it is called.

Wins

  • one credential-failure family, not two
  • RA errors gain set / endpoint context
  • resolveCredentials gets its first test
  • provider stops arming a deferred trap
  • locality: a new failure mode is added once
  • leverage: the readiness rule ships with the mode switch

Problem

The project already wrote the rule down, in test/model/CAPABILITIES.md: “The prime rule for fakes: declare only what you truly model. An optimistic fake that claims what it fakes poorly is how a suite passes against broken code.” FakeS3 obeys it — it re-implements ADR-0083's guard faithfully and documents what it does not model. The nine object-literal adapters in src/ declare nothing, and several claim success for operations whose whole point is that they can refuse.

Solution

Not one god-fake — the tiers differ on purpose. Give the seam a constructor: a factory that returns an adapter with honest defaults (a putFile that verifies, a getStream that ends), which a test narrows by passing only what it wants to vary. Two adapters means a real seam; ten means the seam deserves a shape.

Wins

  • ADR-0083's guard is exercised by default, not stubbed away
  • locality: a new seam method updates one factory
  • the two copy-pasted adapters collapse
  • a test declares only what it varies
  • leverage: CAPABILITIES.md covers all ten
  • the unit tier stops disagreeing with the model tier
Respects ADR-0019 and ADR-0049 — mock at s3.mjs, and let the tier live where it lives. This adds no tier and moves no test; it gives the existing ones a shared way to say what they are pretending.

F · The bucket-scan ordering rule is prose, not code

Worth exploring
src/lib/remote.mjs · src/lib/referenced.mjs · src/commands/cleanup.mjs · src/commands/delete.mjs

The safety property — snapshots must be listed before objects, so a concurrent backup can only make the scan over-estimate what is referenced — is stated in nine separate doc comments and enforced by none of them. ADR-0090's compaction added a third phase and a cross-command writer, so the rule now spans modules that don't import each other. A scan that returns its phases in the wrong order is a silent data-loss bug with a green suite. (The pass-11 trigger for this — “a third scanner appears” — did not fire; the phase count grew instead.)

Deepening: one module owns “scan the bucket safely” and returns a result whose construction order is the ordering; callers can't assemble one wrongly because they never assemble one.

★ Top recommendation

A · find cannot see a UNC path.

It is the only candidate this pass with a live behaviour fault behind it, and the fault disables a documented end-to-end workflow: under ADR-0089, find is the only route to the content hash delete takes as its operand, so content backed up from a network share cannot be located or removed. Nothing refuses a UNC root on the way in, so the data gets there.

It is also the cleanest deepening on the list. The bug exists because one boolean is asked two different questions, so the fix and the architecture are the same edit: let path-match.mjs own path spelling and return an answer rather than a flag. And it closes a seam that has never had a test file at all — the smallest module here with the largest untested blast radius.

Then: B (small, deletes test workarounds, and the clock seam already exists), then D (pays into every tier at once), then C (largest, and the one whose shape most deserves a grilling first).
